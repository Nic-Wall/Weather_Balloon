# Dockerfile
No more Python venv, no more different named development packages, no more version mismatches. Now every start-up of the container will result in the same build every time, no hassle required (except the install of Docker). This assumes, if you wish to build the project yourself, you have Docker installed. The container spins up, downloads the necessary packages to build the project and copies the associated files from this project's source, including the Makefile. It then runs the Makefile.
Some documentation on creating a Dockerfile comes from [Docker's documentation](https://docs.docker.com/get-started/docker-concepts/building-images/writing-a-dockerfile/) itself...
The script for installing packages en-mass was found [here](https://askubuntu.com/questions/252734/apt-get-mass-install-packages-from-a-file)
```Dockerfile
# Pulling from https://hub.docker.com/_/debian?tag=stable-20260918-slim
FROM debian:bookworm-20260918-slim
COPY packages.txt /tmp/packages.txt
RUN apt-get update && apt-get install -y $(grep -vE "^\s*#" /tmp/packages.txt | tr "\n" " ")
RUN useradd -m -u 1000 dev
USER dev
WORKDIR /WB
```
... then built the container with...
```
# docker build -t nicholas/weatherballoon .
```
... the compose builds and runs the container...
```compose.yml
name: weather_balloon
services:
  build_env:
    image: nicholas/weather_balloon:local
    build: ./
    user: 1000:1000
    stdin_open: true
    tty: true
    command: bash
    volumes:
      - ./:/WB
    network_mode: "host"
```
NOTE: `network_mode: "host"` was used because the MTU of the docker container failed to pull some files from gitlab without it.
... to start the container with the compose...
```
# docker compose -f compose.yml run --rm build_env
```
This way I can run tests in the container as the `dev` user. When the build process is complete I'll have it run the Makefile in the Dockerfile, that way everything is built and ready to be viewed with just the container being built and run once!

# Learned in the Process Of...
NOTE: Not specifically about Makefiles
- `gen_initramfs.sh` can take a list of files to create in the compressed initramfs. So the Makefile doesn't have to create the `/dev/console` and `/dev/null` my shell script did. Permissions can be set and the device nodes can be created during initramfs generation with the list file at `srcs/configs/gen_initramfs.list`. This method also works to change file permissions, so the `root:root` permission can be set on `/bin/busybox` without the need to be `root`.
- In my experience using stamp files for rules that generate multiple files is best practice over pinning the rule to a single file out of the multiple generated. If a file is created and then changed later in the build process BUT the build process is interrupted, Make may consider the file in a usable state, even if it is not. Creating and verifying based on a stamp file (using `touch $@` to create the file `.kernel_stamp` based on the rule of the same name) ensures the build process completes successfully and the necessary file is in a usable state. It's usefulness is doubled because of the timestamps Make works off of. Recompilation of certain rules can be changed simply by touching the stamp files!
