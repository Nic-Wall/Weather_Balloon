- `d`: Deletes the only existing partition.
- `l`: Displays the partition table. Displaying numerical identifiers for each partition type. Notably, `ef` is EFI FAT32 and `83` for Linux.
- `n`: Creates a new partition. Both newly created partitions are primary (`p`), not extended (`e`). Their default number assignments are acceptable. The starting sector is fine as well, but the last sector is set for `+128M` and `+1G` for the FAT32 and Linux partitions respectively.

2. `gcc` and `clang` (being newer versions than those used in the forum posts) add bloat to the `bl31.elf`.

# Reflection
Missing packages, non-stable versions, and a little mishandling of linker scripts later. What was learned?
Primarily, while no documentation suggested using a more stable release of trusted-firmware-a it probably should have been one of the first tests instead of relying on mainline. All the reports of the `pmusram` issues were for the main version of trusted-firmware-a and reported within a year of this install. Oddly, forum posts reported patches, which are present in this install, resolved the issue. While that appears to not be the case.
Through experimentation and searching the proper way to read mailing lists and `diff`'s, write patches, trace error codes to files, and download differing branches using `git` was learned.
Thorough reading of documentation could have saved some headaches at the start of the project given the RAM issues caused by compiling for `evb` instead of `rockpro64`. Although, reading the error and discovering the discrepancy between the boot reporting LDDR3 RAM instead of LDDR4 (which is actually present on the RockPro64) was a rewarding hint to notice and deduce from.
Lastly, working backwards from a custom compilation to the bare minimum configuration to troubleshoot a failing boot saw success. While the information in Mastering Embedded Linux Development is immensly informative, it's clear every implementation will not work on the architecture available for this project compared to that which is used as examples in the book. Though, this was anticipated and troubleshooting differences is sought after to better understand the process, recognize patterns, and practice finding solutions (like this)!
So, what changes were made in `make menuconfig` that prevented U-Boot from booting?
- **Environment**
	- Environment is in a EXT4 filesystem: Selected
	- Environment is in an MMC device: De-Selected
	- Name of the block device for the environment: `mmc`
- **SPL configuration options**
	- Support EXT filesystems: Selected
- **Boot options**
	- Enable a default value for bootcmd: (Was already, but double checked) Selected
	- bootcmd value:
		- Was... `bootflow scan -lb`
		- Now... `echo 'no bootcmd yet'`
Pressing `?` on each option changed gives a brief overview of what it does and helps deduce why a change to it may prevent proper booting...
- **Environment**
	- Environment is in an EXT4 filesystem
		- Should be selected if the configuration file for the environment is in an EXT4 file system. It is not for this build, placed at an  offset of 16384 U-Boot and it's default environment configuration file reside in a FAT-32 partition.
		  By default this option is de-selected and and `Environment is in SPI flash` is selected instead.
	- Environment is in a MMC device
		- Same as above but for an MMC device instead of EXT4 file system.
		  By default this option is not selected.
	- Name of the block device
		- A string that is used as the name of the block device for the EXT4 file system. This option is only present if `Environmnet is in a EXT4 filesystem` is selected. Therefore, it is not selected by default, because it does not exist.
- **SPL Configuration options**
	- Support EXT filesystems
		- Enables EXT file system support with SPL, allowing U-Boot to be loaded from an EXT file system from within SPL. Since SPL resides in SPI flash, this setting, whether enabled with `Environment is in an EXT4 filesystem` or not, does not make a difference.
- **Boot Options**
	- Enable a default value for bootcmd
		- Provide a default value for the bootcmd entry in the environment. Notably, if autoboot is enabled this command runs automatically.
	- Bootcmd value
		- `bootflow scan -lb`: [This](https://docs.u-boot.org/en/stable/usage/cmd/bootflow.html) scans for bootflows in all bootdevs (`bootflow scan`), lists them (`-l`), and attempts to boot each (`-b`).
		- `echo 'no bootcmd yet'`: Just  a plain echo command, so U-Boot doesn't boot into any bootdevs it finds automatically. This was likely done by the book to show off U-Boot commands without requiring the user to interrupt U-Boot.
The boot probably failed due to the `Environment is in an EXT4 filesystem` setting with no configuration existing in the file system (a mismatched file system at that). Likely skipping over the SPL/ TPL in SPI flash.
It's clear, it's not enough to follow directions but to understand them as well. Thankfully, for a beginner, U-Boot provides sane defaults compatible with most boards. From here, making changes to U-Boot is dependent on needs. Of course, for curiosities sake exploration of the options will continue but won't be documented here.
