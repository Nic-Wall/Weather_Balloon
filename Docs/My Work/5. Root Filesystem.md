So set the owner to `root`...
```shell

```
... then...
```shell

```
... set the user who owns the binary (`u`) execution rights (`+s`). Now all the symlinked binaries in `rootfs/bin` (that are pointing to `rootfs/bin/busybox`) have permissions `lrwxrwxrwx` while `rootfs/bin/busybox` has `-rwsr-xr-x` (and is owned by `root:root`) meaning any user can read and execute the binary as `root` when it's required, otherwise running the binary as the user.
There should be no need to copy `.so` files as the libraries were compiled into the binary, not linked. Space is also saved because the static compilation stripped the `busybox` binary. The proof of which can be seen below...

# Device Manager and Device Nodes
First, to create the bare minimum required device nodes; `dev/null` and `dev/console`. These are required to send messages to the kernel and to cleanup unused data. If these aren't present the system may not boot and certainly won't be accessible. So...
```shell
cd rootfs

sudo mknod -m 666 dev/null c 1 3

sudo mknod -m 600 dev/console c 5 1
```
Using a device table I created a static foundation of the `rootfs` and its permissions. Once completed the kernel needs to know where the file is to create the cpio archive from the table. This is done as an exercise and evidence of knowledge, this `device_table.txt` isn't used in the final build. The creation of the table...
```shell
pwd
# Returns...
/home/nicholas/Projects/WeatherBalloon/by_hand

vim device_table.txt
```
... and in that `device_table.txt` file...
```device_table.txt
dir /bin 775 0 0
dir /sys 775 0 0
dir /tmp 775 0 0
dir /dev 775 0 0
nod /dev/null 666 0 0 c 1 3
nod /dev/console 600 0 0 c 5 1
dir /home 775 0 0
dir /proc 775 0 0
dir /lib 775 0 0
```
... basic data indicating what is a directory (`dir`) or device node (`nod`), the name of the object, it's permissions, `uid`, `gid`, and (in the case of the device nodes) it's dev type (`c` for byte-by-byte access) as well as the major and minor numbers required by the kernel to route file requests. To keep editing of all things easier, I won't bake the initramfs into the kernel (although it would likely decrease boot time). Instead, I'll let `gen_initramfs.sh` generate a table for me!

# `inittab`
Next up is the `inittab` file used to tell the `init` command what processes to start, [namely daemons and shell](https://www.ibm.com/docs/en/aix/7.1.0?topic=files-inittab-file). It'll be pretty simple to start, at least until I write a few scripts to launch sensors on boot. Just a call to start a script for mounting necessary files systems and launch a shell.
```/etc/inittab
::sysinit:/etc/init.d/rcS
::respawn:/sbin/getty 115200 console
::respawn:/sbin/syslogd -n
```
The first line runs the `/etc/init.d/rcS` bash script before `init` tries to access the console. The second launches `getty`, a program that initiates the login procedure. Should `getty` stop for any reason it's restarted (`respawn`) with the provided baud rate (`115200`) in the console virtual file (usually `tty#`). The third starts accumulating log messages that will be put in `/var/log/messages`, restarting if it stops for some reason (`respawn`), and running in the foreground (`-n`). All that needs in `/etc/init.d/rcS` right now is the following...
```/etc/init.d/rcS
#!/bin/sh
mount -t proc proc /proc
mount -t sysfs sysfs /sys
```
... and to make it executable...
```shell
pwd
# Returns...
/home/nicholas/Projects/WeatherBallon/by_hand/rootfs

sudo chmod +x etc/init.d/rcS
```
# Basic Users
Despite the security of the board being a near non-issue due to it being almost impossible for someone to physically access and it intentionally being disconnected from the wider internet it's still best practice (and an easy exercise) for it to run as a non-root user. These accounts are created in `/etc/passwd`, with their passwords stored as hashes in `/etc/shadow`, and added to groups in `/etc/group`. The three basic users need are `root`, a user for daemon processes, and a non-root user...
```/etc/passwd
root:x:0:0:root:/root:/bin/sh
daemon:x:1:1:daemon:/usr/sbin:/bin/false
sensorMonitor:x:2:2:sensorMonitor:/home/sensorMonitor:/bin/sh
```
... then the groups...
```/etc/group
root:x:0:
daemon:x:1:
sensorMonitor:x:2:
```
... and lastly the actual passwords with pre-hashed strings...
```/etc/shadow
root:$6$weatherballoon$D4KoZqdBXwabJFo6ZTvWo/cVZDXcmGPyYce8Pudlh8j2H.nhg6yJLF1BGa8IxaEzICPGdU5ED998..UkeU.ox1:10933:0:99999:7:::
daemon:*:10933:0:99999:7:::
sensorMonitor:$6$balloonweather$KpAjdbuJX5/m1FzIwYWvksGCn0GY7EG7SVZvwpDDzzHtLUy0FxpEhpmEznCy78HZSWfyNWt6I/8N1UIbyeHf1.:10933:0:99999:7:::
```

Where the fields are: user, password hash (with optional salt), last password change, minimum days before next password change is permitted, maximum number of days password can exist before it must be changed, number of days before password expiry in which user is warned a password change will be required, number of days before password expiry (account becomes disabled after), number of days until account expiry.

# `mdev`
With `CONFIG_DEVTMPFS` enabled in the kernel configuration file, verified with a quick...
```shell
pwd
# Returns...
/home/nicholas/Projects/WeatherBalloon/by_hand

cat build_arm64/.config | grep CONFIG_DEVTMPFS
# Returns...
CONFIG_DEVTMPFS=y
CONFIG_DEVTMPFS_MOUNT=y
```
I also need to mount `devtmpfs` to `/dev` along with `proc` and `sys` in `/etc/init.d/rcS`. So...
```/etc/init.d/rcS
#!/bin/sh
mount -t proc proc /proc
mount -t sysfs sysfs /sys
mount -t devtmpfs devtmpfs /dev
```
The `CONFIG_DEVTMPFS_MOUNT` kernel option only sees the kernel automatically mounting `devtmpfs` after the root filesystem is mounted. But this option does nothing when just booting `initramfs`.
Then, to keep track of new devices being added and to create nodes automatically for them, I'll need to start running `mdev` with my init system (like the mounting of `proc`, `sys`, and `devtmpfs`). According to *Mastering Embedded Linux Development* this is done by adding `mdev` as hot plug client, putting it's path in `/proc/sys/kernel/hotplug`. The [default agent at this path](https://man7.org/linux/man-pages/man5/proc_sys_kernel.5.html) is `sbin/hotplug`, but I'll be using BusyBox's implementation (`mdev`) instead. To ensure the numerous `HOTPLUG` options are enabled in my kernel...
```shell
cat build_arm64/.config | grep HOTPLUG
# Returns...
...
CONFIG_ACPI_HOTPLUG_MEMORY=y
CONFIG_ARCH_ENABLE_MEMORY_HOTPLUG=y
CONFIG_MEMORY_HOTPLUG=y
# CONFIG_HOTPLUG_PCI_PCIE is not set
CONFIG_HOTPLUG_PCI=y
CONFIG_HOTPLUG_PCI_ACPI=y
...
```
Then to add `mdev` I'll write it's path to `/proc/sys/kernel/hotplug` in the `rcS` and run `mdev` with the `-s` option to start scanning the `/sys` directory for information on current devices, which it then uses to create nodes in `/dev`.
```/etc/init.d/rcS
#!/bin/sh
mount -t proc proc /proc
mount -t sysfs sysfs /sys
mount -t devtmpfs devtmpfs /dev
echo /sbin/mdev > /proc/sys/kernel/hotplug
mdev -s
```
The book also notifies me the default mode is `660` and `root:root` (although [BusyBox's official example](https://github.com/brgl/busybox/blob/master/examples/mdev.conf) shows using UID and GID (`0:0`) which is what I'll use instead), suggesting to change it along with `null`, `random`, and `urandom` with a file in `/etc/mdev.conf`, like so...
```/etc/mdev.conf
null 0:0 666
random 0:0 444
urandom 0:0 444
```
This sets a static assignment to these three device nodes modes/ ownership instead of using the default mentioned above. This doesn't create the nodes, it only changes their mode/ ownership if `mdev` finds a regex match when scanning `sys`.
# Generating `initramfs`
I'll use the provided [`gen_initramfs.sh`](https://github.com/torvalds/linux/blob/master/usr/gen_initramfs.sh) script to create the cpio archive...


```shell
cp ../build_arm64/usr/gen_init_cpio ./usr/

./usr/gen_initramfs.sh -o ../initramfs.cpio -u 1000 -g 1000 ../rootfs

cd ..

pwd
# Returns...
/home/nicholas/Projects/WeatherBalloon/by_hand

ls | grep initramfs
# Returns...

```
Then I just need to compress it with `gzip` and add the U-Boot header manually...
```shell
gzip initramfs.cpio

./u-boot/tools/mkimage -A arm64 -O linux -T ramdisk -d initramfs.cpio.gz uRamdisk

ls | grep initramfs
# Returns...
initramfs.cpio.gz
```
... for the arm64 architecture (`-A`), targeting a Linux operating system (`-O`) (where to place the image in memory, how to pass boot arguments, etc.), with a ramdisk payload (`-T`) (decompressed and mounted as `rootfs`), using `initramfs.cpio.gz` as the data file (`-d`), all into `uRamdisk` the output file.
Now the ramdisk is ready to be moved to the board.
